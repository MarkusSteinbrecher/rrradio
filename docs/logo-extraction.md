# Station Logo Extraction

This playbook documents the current remote-logo extraction workflow for
Codex and Claude agents. It covers two jobs:

- filling `favicon:` for published stations that have no logo
- replacing weak, generic, HTTP, or third-party logo URLs with better
  broadcaster-hosted remote images

The workflow intentionally prefers remote broadcaster URLs over bundled
files. Only add files under `public/stations/` when the source and usage
rights are clear enough to record in `THIRD_PARTY_NOTICES.md`.

## Source Of Truth

- `data/stations.yaml` is edited by the scraper.
- `public/stations.json` is generated from YAML by `npm run catalog`.
- `public/station-logo-status.json` is generated by `npm run logo-status`.
- `public/station-logo-quality.json` is generated by `npm run probe-logos`
  and is read by `logo-status` when present.
- `.local/curation.db` is a gitignored working database for selecting
  batches and reviewing progress.
- `.cache/logo-scrape-report.json` is the latest scraper report, including
  selected and rejected candidates.

`favicon:` may be:

- a remote HTTPS URL, preferred for scrape batches
- a local `stations/<id>.png` asset, reserved for curated bundled logos
- absent, in which case the UI falls back to generated initials

### Provenance fields

Logo fields track where the URL came from, what kind of asset it is,
and whether we can redistribute a bundled copy. They flow through to
`public/stations.json` and are consumed by the station tracker.

`faviconSource:` — where the logo URL came from:

| Value | Set by |
|---|---|
| `broadcaster-site` | `scrape-logos` (HTML/manifest image from broadcaster homepage) |
| `broadcaster-api` | `harvest-logos` (per-channel image URL from a broadcaster metadata API) |
| `radio-browser` | imported from Radio Browser's favicon field |
| `wiki` | `wiki-logos` (Wikipedia CC-licensed article image) or `migrate-nonfree-logos` (free Commons replacement for a non-free `wikipedia/en` upload — #472) |
| `broadcaster` | bundled local PNG hand-curated from the broadcaster |
| `manual` | explicitly set in YAML by hand |
| `http-upgraded` | mechanical HTTP→HTTPS swap with no content change |

`faviconSourceType:` — what kind of asset the URL points at:

- `bundle`: local `stations/<id>.png`
- `api`: dynamic image endpoint or CDN transform URL
- `cdn`: static remote asset
- `none`: intentionally no logo

`faviconSourceUrl:` records the original upstream URL for bundled local
files. For remote favicons it is usually redundant with `favicon:`.

`faviconLicense:` records usage rights. Common values are `broadcaster`,
`broadcaster-implicit`, `wikipedia`, `cc-by`, `cc-by-sa`, `cc0`, and
`public-domain`. Absent means `unknown`.

`faviconOk: true` is explicit human sign-off. It suppresses URL-heuristic
upgrade churn, but probe errors still need fixing.

Absent `faviconSource` means the URL provenance is unknown. Those stations
stay in the upgrade queue until a known-good source is confirmed.

**Patch format for `apply-logos`** requires a valid `source` key and a
HTTPS remote URL or local `stations/` path:

```json
[
  {
    "id": "station-id",
    "url": "https://example.com/logo.png",
    "source": "broadcaster-site",
    "sourceType": "cdn",
    "license": "broadcaster-implicit"
  }
]
```

Optional keys `sourceUrl`, `sourceType`, `license`, and `ok` are written
as `faviconSourceUrl`, `faviconSourceType`, `faviconLicense`, and
`faviconOk`.

Useful `logo_action` values:

- `scrape-missing`: no logo, or a logo URL that probed as gone
- `scrape-upgrade`: weak/provenance-unknown/poor-quality logo with a homepage
- `probe-logo`: a logo exists but has not been size-probed yet
- `reprobe-logo`: the last probe failed transiently, such as timeout or 429
- `improve-curated-logo`: local bundled logo exists but probes as poor/unknown

## Candidate Queues

Start from a fresh generated catalog and logo report:

```bash
npm run catalog
npm run probe-logos -- --remote
npm run logo-status
npm run curation-db:ingest
npm run curation-db:summary
```

Useful SQLite queries:

```bash
# Count work by country and action.
sqlite3 -header -column .local/curation.db \
  "SELECT country, logo_action, COUNT(*) AS n
   FROM stations
   WHERE logo_action IN ('scrape-missing', 'scrape-upgrade', 'probe-logo',
                         'reprobe-logo', 'improve-curated-logo')
   GROUP BY country, logo_action
   ORDER BY country, logo_action;"

# IDs for one country's truly missing logos.
sqlite3 -noheader .local/curation.db \
  "SELECT group_concat(id, ',')
   FROM (SELECT id
         FROM stations
         WHERE country='AT' AND logo_action='scrape-missing'
         ORDER BY id);"

# IDs for one country's upgrade candidates.
sqlite3 -noheader .local/curation.db \
  "SELECT group_concat(id, ',')
   FROM (SELECT id
         FROM stations
         WHERE country='AT' AND logo_action='scrape-upgrade'
         ORDER BY id);"
```

Use country batches or small exact-ID batches. Avoid full-catalog writes
unless the hit set has already been reviewed.

## Scraper Modes

Always dry-run first:

```bash
npm run scrape-logos -- --mode missing --id id1,id2,id3 --dry-run --concurrency 8
npm run scrape-logos -- --mode upgrade --id id1,id2,id3 --dry-run --concurrency 8
```

Modes:

- `missing`: target stations whose effective catalog favicon is absent.
  Hits are new logos and reduce `missing`.
- `upgrade`: target stations whose current favicon is weak, generic, HTTP,
  third-party, or quality-unknown. Hits are replacements and usually reduce
  `scrape-upgrade`, not `missing`.
- `all`: broad discovery mode. Use only for investigation or with
  `--dry-run`.

The scraper reads the generated `station-logo-status.json` queue when present,
then station homepages from YAML and the generated catalog. It also derives
some homepages from stream URLs, suppresses generic catalog pages like Radio
Browser, discovers HTML meta images, JSON-LD images, and manifest icons, probes
image headers for real format and dimensions, rejects poor or unknown Now
Playing quality, and writes a provenance-rich report to
`.cache/logo-scrape-report.json`.

Every run also prints and stores a `review` block in that report. Treat it as
the review gate before applying anything:

- `duplicateUrls`: same selected candidate reused by four or more stations.
  This can be valid for regional networks, but it catches platform icons and
  site-wide defaults quickly.
- `lowSignalSelections`: selected candidates with low-signal relations
  (`icon`, `shortcut icon`, `mask-icon`), non-OK URL classification, or only
  acceptable NP quality. These need spot-checking.
- `topHosts`: where selected images came from, useful for catching platform
  or parked-domain clusters.

## Per-Channel Art (multi-channel broadcasters)

`scrape-logos` finds **one** logo per homepage, so every sibling channel of a
broadcaster gets the same brand mark. Multi-channel broadcasters (Radio Gong
96.3, bigFM, Gong FM, …) instead publish a grid/slider of **per-channel** cover
images, each labelled with the channel name in `alt` text or the filename
(`Gong 96.3_Top 50_600x600.<hash>.png`). `scrape-channel-art` maps those images
to the right station.

```bash
npm run scrape-channel-art -- --host radiogong.de --dry-run        # one broadcaster
npm run scrape-channel-art -- --id de-radio-gong-96-3-chill-om --dry-run
npm run scrape-channel-art -- --cc DE --min-family 3 --dry-run     # all DE families >=3
npm run scrape-channel-art -- --host radiogong.de --replace        # also upgrade existing
```

How it works:

1. Groups stations into brand families by `familyBucketKey` (`COUNTRY|homepage-host`,
   the same key the dedupe family model uses), skipping aggregator hosts.
2. Fetches each family's homepage plus a couple of same-host `streams/webradio`
   subpages it links to (`--streams-pages`, default 2).
3. Extracts every labelled `<img>`, derives a label from `alt` or the filename,
   strips the shared brand prefix, and **matches each image to a station** by
   collapsed-string containment + token overlap against the station's `shortName`
   (matcher lives in `tools/lib/channel-art-match.mjs`, unit-tested).
4. Assigns art only on a **confident, unambiguous, byte-verified** match —
   1:1, never the same image to two channels. Unmatched/ambiguous channels are
   reported and left for the homepage/brand logo fallback; the tool never guesses.

Flags: `--id` / `--host` / `--cc` narrow the run (and lift the `--min-family`
floor); default is **fill-missing** (only stations with no favicon), `--replace`
also upgrades an existing logo to the matched per-channel art. Writes
`broadcaster-site` / `cdn` / `broadcaster-implicit` provenance, same surgical
YAML insert/replace as `scrape-logos`. Report: `.cache/channel-art-report.json`
(includes `unmatched` and `ambiguous` rows — review these before a `--replace`).

After a real run, regenerate and verify exactly as for `scrape-logos` (catalog,
favicon-variants, check-catalog, check-duplicates, build).

## Broadcaster-API Logos (metadata-API channel art)

When a broadcaster exposes per-channel art through the **same metadata API we
already call for now-playing** (the SRG SSR integration layer is the proven
case), `harvest-logos` beats scraping: the URLs are authoritative,
broadcaster-hosted, and licence-clean, and the station → channel join is exact
(by the id already in `metadataUrl`). See *Broadcaster-API logos* in
`docs/operations.md` for the full workflow. In short:

```bash
npm run harvest-logos                          # missing-only (safe inserts)
npm run harvest-logos -- --upgrade-generic     # + weak/site-default icons
npm run harvest-logos -- --include-existing     # forced idempotent re-harvest
npm run apply-logos -- --in internal/logos/broadcaster-api.json [--replace]
```

The join + write policy are pure and unit-tested in
`tools/lib/broadcaster-logos.mjs`; add a broadcaster by adding an adapter there.
`faviconSource: broadcaster-api`. Prefer this over `scrape-logos` /
`scrape-channel-art` whenever a metadata API already serves the art. Caveat: the
SRG `imageUrl` is a 16:9 branded card — busier than a wordmark for the list
icon, so default policy leaves an existing good logo (e.g. SRF's Commons
wordmarks) untouched.

## iOS-local Catalog: Favicon Inheritance

`public/stations-ios-local.json` (built by `npm run catalog:ios-local`) is the
local-only iOS *test* catalog: the curated set **plus** the full Radio Browser
candidate pool, one row per playable source, HTTP streams included. It is **not**
the shipped web catalog. Each row resolves its favicon through four tiers, in
order:

1. **curated catalog art** — the candidate's `matchedCatalogId` station's favicon
   (per-channel art flows here automatically once it lands in `stations.json`);
2. **`akaStationUuids` alias** — when the uuid/streamUrl matcher in
   `build-sources` *can't* link a stale RB record (different uuid, dead old
   stream, drifted name) to the curated station it really is, list that record's
   `stationuuid` under `akaStationUuids:` on the curated YAML row so this catalog
   inherits the correct per-channel art;
3. **raw Radio Browser favicon** (HTTPS only);
4. **family brand mark** — an RB orphan from a broadcaster we curate, carrying its
   family's name-token core (gated by `detectFamilies`, *not* a bare host bucket),
   gets the family's representative logo (`faviconSource: catalog-family-brand`)
   rather than rendering blank.

This is why a Radio Gong 96.3 channel can have perfect per-channel art in the
shipped catalog yet still show blank rows in the iOS-local catalog: those rows are
RB's own (often pre-HTTPS-migration) duplicate records, not our curated stations.

**Freshness is gated.** `check-catalog` fails when any iOS-local row linked to a
curated station (`localMatchedCatalogId`) lacks a favicon that station actually
has — i.e. the artifact drifted behind a logo change. Fix by rebuilding:

```bash
npm run catalog:ios-local   # then commit public/stations-ios-local.json
```

Run this after any curated-favicon change (per-channel art sweeps especially), the
same way you regenerate `stations.json`.

## Review Rules

Do not apply a scrape run blindly. Review the report and spot-check images.

List selected replacements:

```bash
node -e "const r=require('./.cache/logo-scrape-report.json');
for (const row of r.rows.filter(x => x.action === 'insert' || x.action === 'replace')) {
  console.log([row.id, row.rel, row.from || '', row.to, row.scrapedPage, row.score].join('\t'));
}"
```

Download borderline candidates to `/tmp` and inspect them:

```bash
mkdir -p /tmp/rrradio-logo-review
curl -L --fail -o /tmp/rrradio-logo-review/<station-id>.png '<candidate-url>'
sips -g pixelWidth -g pixelHeight /tmp/rrradio-logo-review/<station-id>.png
```

Accept:

- station-specific logos or station-specific square artwork
- broadcaster-hosted logo files with logo-like filenames
- manifest icons that are clearly station-specific
- higher-resolution variants of an existing station-specific image
- HTTPS replacements for an otherwise identical HTTP logo

Reject:

- generic app icons, favicons, platform icons, or browser placeholder icons
- article images, screenshots, hero photos, playlist art, or one-off show art
- government, parent-company, or site-wide marks when the station has a
  more specific identity
- Apple Music, Spotify, YouTube, app-store, TuneIn, MyTuner, Streema, or
  Radio Browser marks
- no-op replacements where `from` and `to` are equivalent
- ORF regional generic touch icons or similar broad broadcaster defaults
  when a station-specific logo already exists
- any non-HTTPS logo unless the station has an explicit `httpAllowed`
  rationale, which should be rare

When in doubt, leave the existing URL in place and file a follow-up issue
instead of making the catalog noisier.

## Apply A Reviewed Subset

### Single-country (simple) workflow

After review, rerun with only accepted IDs and without `--dry-run`:

```bash
npm run scrape-logos -- --mode upgrade --id accepted-id-1,accepted-id-2 --concurrency 8
```

### Multi-country consolidated workflow (preferred for parallel agent runs)

Each agent writes its accepted pairs to a JSON patch file instead of
modifying `stations.yaml` directly. This avoids per-PR rebases when
running multiple countries in parallel.

**Agent output format** (`/tmp/rrradio-logo-patches/<cc>-accepted.json`):

```json
[
  { "id": "station-id", "url": "https://example.com/logo.png", "source": "broadcaster-site" },
  …
]
```

**Consolidate and apply all patches in one pass:**

```bash
# Merge all patch files into one
node -e "
  const fs = require('fs');
  const dir = '/tmp/rrradio-logo-patches';
  const all = fs.readdirSync(dir)
    .filter(f => f.endsWith('.json'))
    .flatMap(f => JSON.parse(fs.readFileSync(dir+'/'+f,'utf8')));
  fs.writeFileSync(dir+'/all.json', JSON.stringify(all, null, 2));
  console.log('merged', all.length, 'entries from', dir);
"

# Apply to stations.yaml (--replace handles both inserts and upgrades)
npm run apply-logos -- --in /tmp/rrradio-logo-patches/all.json --replace
```

Then regenerate and verify:

```bash
npm run catalog
npm run catalog:fts
npm run probe-logos -- --remote
npm run logo-status
npm run curation-db:ingest
npm run curation-db:summary
npm run check-catalog
npm run check-duplicates
npm test -- --run tools/logo-quality.test.mjs
npm run build
git diff --check
```

`npm run check-duplicates` rewrites `public/station-duplicates.json` with a
timestamp. If only `generatedAt` changed, restore it before committing:

```bash
git restore public/station-duplicates.json
```

Commit only source and meaningful generated artifacts. Typical logo-only
remote URL batches touch:

- `data/stations.yaml`
- `public/stations.json`
- `public/station-logo-status.json`
- sometimes the separate iOS repo's `rrradio/Resources/stations.fts5.db`,
  when catalog fields affecting the iOS search index changed

## Known Current Lessons

- The truly missing queue is mostly `stream-only`; many rows only have
  stream-host or platform pages and produce no safe logo.
- The upgrade queue has higher yield, but it also produces more false
  positives. Manual review is mandatory.
- Country-targeted runs work well for Claude agents because the review set
  stays small and results are easy to summarize.
- Keep skipped candidates visible in the PR or issue notes when they explain
  why a country still has missing or weak logos.
- Multi-country parallel runs should use the consolidated workflow (patch
  files + `apply-logos --replace`) to avoid per-PR rebases on stations.yaml.
