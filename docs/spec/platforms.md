# Platform Specification

rrradio has one product contract and multiple platform implementations. Shared
behavior should remain recognizable across web, iOS, and Android, while each
platform uses native playback, storage, and OS integration.

## Shared Contracts

- Catalog entries come from `public/stations.json`, generated from YAML.
- Publishable station statuses are `working`, `icy-only`, and `stream-only`.
- Station identity is stable by station `id`.
- Radio Browser binding, drift review, broadcaster metadata fields, and
  curation rules are defined in [Operations](../operations.md).
- Search must be whitespace-insensitive and tolerant of common diacritic input.
- A platform may cache the catalog, but cache refresh must never require an app
  release when the published JSON changes.
- User-entered stream URLs must be treated as private user data.
- Telemetry and diagnostics must avoid stack traces, search queries, stream
  URLs, track titles, artist names, and arbitrary user-entered strings.

## Web

The web app is the public, installable PWA and remains the broadest catalog and
metadata proving ground.

Current implementation shape:

- Vite, TypeScript, vanilla DOM.
- `HTMLAudioElement` for MP3/AAC streams.
- `hls.js` for HLS on non-Safari browsers.
- Media Session API where the browser supports it.
- `localStorage` for favorites, recents, custom stations, wake state, and UI
  preferences.
- Cloudflare Worker for allowlisted broadcaster proxying and public reports.

Platform constraints:

- Autoplay requires a user gesture.
- Background behavior depends on the browser and OS.
- Lock-screen controls depend on Media Session support.
- Local storage may be cleared by the user or browser privacy policy.
- No account system and no server-side user library.

## iOS

iOS is the current reference for native app behavior.

Current implementation shape:

- SwiftUI app generated by `xcodegen`.
- AVFoundation/AVPlayer playback.
- Background audio capability.
- MPNowPlayingInfoCenter and MPRemoteCommandCenter for lock-screen,
  Bluetooth, and AirPods controls.
- UserDefaults-backed local library.
- CloudKit private database sync for supported library and preference data.
- watchOS companion app that remotely controls iPhone playback.
- Native map, wake alarm, sleep timer, local diagnostics, listening history,
  theme/language/landing preferences, and station lists.

Platform constraints:

- iCloud may be unavailable, disabled, unsigned, or signed into a different
  account. The app must stay fully local in those cases.
- iOS can suspend or force-quit the app; wake-to-radio is best effort unless
  audio is kept alive.
- Real lock-screen, background audio, watch, and wake behavior require device
  testing.

## Android

Android has an existing native scaffold in `android/`. The next Android work is
alignment with this spec and the richer iOS behavior, not a from-zero port.

Current implementation shape:

- Kotlin.
- Jetpack Compose for UI.
- Media3/ExoPlayer for stream playback.
- MediaSessionService for background playback and notification controls.
- DataStore for favorites, recents, and custom stations.
- Catalog decoding and cache-backed network loading.
- Search parity for station names, tags, countries, and whitespace-insensitive
  matches.
- Sleep timer cycle.
- Basic ICY `StreamTitle` parsing and bounded ICY metadata fetcher.

Alignment target:

- Match the product behavior of the iOS native app where Android has equivalent
  OS primitives.
- Stay local-only for user library data.
- Do not attempt CloudKit compatibility.
- Defer any shared account or cross-platform sync backend to a separate ADR.
- Add Room or another local database only when station lists, history, or
  catalog search need queryable storage.
- Add WorkManager, AlarmManager, or exact-alarm permissions only after the
  wake-to-radio behavior is scoped.

Android-specific open decisions:

- Whether Android Auto is in scope for v1 or only generic media controls.
- Whether exact alarms are acceptable for wake-to-radio, given permission and
  battery policy friction.
- Whether the Android catalog search needs a bundled index or can start with an
  in-memory matcher.
- Whether watch/companion surfaces are out of scope or future Wear OS work.
